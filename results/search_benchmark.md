# Search benchmark

Generated by `python -m scripts.benchmark_search`. Every number below comes from that run;
raw rows are in `search_benchmark.csv`.

## Setup

- Dataset: 5,000 users, 200 hotels, 10,000 rooms, 200,000 bookings, 169,958 payments (`scripts.seed` defaults, fixed random seed).
- Queries, exactly as the application sends them (same SQL, same parameter types):
- `city_search`: `GET /availability?city=`: every hotel in a city with a suitable free room
- `hotel_search`: `GET /hotels/{id}/availability`: free rooms of one hotel
- `worker_sweep`: worker: expire lapsed holds (the real UPDATE, rolled back after each execution)
- Index states:
- **none**: no index on bookings (GiST constraint dropped, 0003 downgraded)
- **btree**: B-tree on bookings(room_id) only (GiST dropped, 0003 downgraded)
- **production**: production schema (GiST exclusion index + 0003)
- Dropping the exclusion constraint also removes the double-booking guarantee, which is why
  this only ever happens on the test database.
- Each query and state: 10 warm-up executions, then 100 timed executions over a
  fixed, seeded list of cities, hotels, dates and party sizes. Every state uses the same list.
- Latency is client-side wall time (execute + fetch), so it includes the round trip from
  Python to PostgreSQL in Docker on the same machine. EXPLAIN times are server-side only,
  for the first parameter set.
