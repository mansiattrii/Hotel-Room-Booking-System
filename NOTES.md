## Milestone 1: Setup and schema

### What was built

- Project skeleton, pinned dependencies, ruff config, `.env.example`.
- `docker-compose.yml` with PostgreSQL 16 (named volume, `pg_isready` healthcheck). An init
  script creates a second database, `hotel_booking_test`, used by pytest and the
  concurrency experiment so they never touch development data.
- `config.py`: every setting comes from environment variables (`pydantic-settings`).
- `db.py`: one SQLAlchemy engine and a session-per-request dependency.
- One hand-written Alembic migration for the full schema.
- `GET /api/v1/health`: runs `SELECT 1`; 200 if the database answers, 503 otherwise.
- A shared error format `{"error": {"code", "message"}}` for every non-2xx response.
- JSON-lines logging through the standard `logging` module.
- Tests that hit the real database with raw SQL to prove each constraint works.

### Schema in one picture

```
hotels 1──* room_types 1──* rooms 1──* bookings *──1 users
hotels 1──────────────────* rooms            bookings 1──0..1 payments
```

### Key decisions

**Sync, not async.** The bottleneck is the PostgreSQL connection pool, not Python threads.
Sync code keeps transactions, `SELECT ... FOR UPDATE` and isolation levels easy to read.
FastAPI runs sync endpoints in a thread pool, so requests still run in parallel and the
race condition in the concurrency experiment is real. Async would pay off for thousands of
slow concurrent connections (websockets, many outbound HTTP calls), which this API does not have.

**Hand-written migration.** Autogenerate cannot emit `CREATE EXTENSION btree_gist` and
renders the partial exclusion constraint poorly. The models still declare every constraint
so the code documents what the database enforces, but the migration is the source of truth.

**`NUMERIC(10,2)` for money.** Floats are binary fractions, so `0.1 + 0.2 != 0.3`. NUMERIC is
exact decimal arithmetic; Python reads it as `Decimal`.

**Status and role as `VARCHAR` + `CHECK`, not PostgreSQL `ENUM`.** Both restrict values.
Adding a value to an ENUM needs `ALTER TYPE` (and historically could not run inside a
transaction); changing a CHECK constraint is an ordinary migration.

**`BIGINT GENERATED BY DEFAULT AS IDENTITY` primary keys.** Identity columns are the
SQL-standard replacement for `SERIAL`. BIGINT because bookings is the table that grows
without bound; using it everywhere keeps FK types consistent.

**Composite foreign key `rooms(hotel_id, room_type_id) → room_types(hotel_id, id)`.**
A plain FK on `room_type_id` would allow room 101 of Hotel A to point at a room type of
Hotel B. The composite FK makes that impossible. It needs `UNIQUE (hotel_id, id)` on
room_types as its target, even though `id` alone is already unique.

**Exclusion constraint for double booking.**
```sql
EXCLUDE USING gist (room_id WITH =, daterange(check_in, check_out, '[)') WITH &&)
WHERE (status IN ('held', 'confirmed'))
```
Read it as: "no two rows may have equal `room_id` AND overlapping (`&&`) date ranges, among
rows that are held or confirmed". A UNIQUE constraint can only reject *equal* values; an
exclusion constraint generalises that to any operator, here "overlaps". It is enforced with
a GiST index, and `btree_gist` is the extension that lets a plain `bigint` (`room_id`) sit in
a GiST index next to the range.

**Half-open range `[)`.** A stay from the 10th to the 15th occupies the nights of the
10th–14th. The guest leaves on the 15th, so the next guest can arrive on the 15th.
`[10, 15)` and `[15, 18)` do not overlap; with a closed range `[]` they would share the 15th
and the back-to-back booking would be wrongly rejected. Tested in
`test_back_to_back_bookings_allowed`.

**Partial (`WHERE`) constraint.** Cancelled and expired bookings stay in the table as history
but must not block the room, so they are excluded from the constraint.

**Small extra constraints that turn bugs into errors.**
- `email = lower(email)`: the app normalises emails; the DB rejects anything that slipped
  through, so `A@x.com` and `a@x.com` can't become two accounts.
- `status <> 'held' OR hold_expires_at IS NOT NULL`: a hold without an expiry would block a
  room forever.
- `guests > 0`, prices positive, `star_rating BETWEEN 1 AND 5`.

**Additions to the given schema.**
- `bookings.guests`: needed to validate against room capacity, and it lets the idempotency
  check compare a repeated request's body against the stored booking without an extra
  "request hash" column.
- `UNIQUE (hotel_id, name)` on room_types: two "Deluxe" types in one hotel is a data error.

### Normalisation

The schema is in 3NF with one deliberate exception: `rooms.hotel_id`. It is derivable from
`room_type_id → room_types.hotel_id`, i.e. a transitive dependency. It is kept because:
1. `UNIQUE (hotel_id, room_number)` needs both columns in the same table.
2. "Rooms in hotel X" is a common query that would otherwise need a join.
The usual risk of denormalisation, the two copies disagreeing, is removed by the composite
foreign key, which forces them to match.

`bookings.total_price` is also stored rather than computed: prices change over time, and a
booking must keep the price the guest agreed to.

### Indexes in this milestone

Only those that come with constraints: primary keys, the UNIQUE constraints, and the GiST
index behind the exclusion constraint. Indexes for search and booking queries are added in
Milestone 3 as a separate migration, next to the queries that use them. That also lets the
Milestone 4 benchmark measure "without vs with" by downgrading and re-applying just that
migration.

### A bug found while verifying `/health`

With the db container stopped, `/health` hung forever instead of returning 503.
Docker Desktop's port proxy keeps accepting TCP connections on the host port even when the
container behind it is down. The driver's TCP connect succeeds, then waits indefinitely for
the PostgreSQL handshake. The unit test hadn't caught it because it used a closed port,
which fails instantly.

Fix: `connect_timeout` on the engine (`DB_CONNECT_TIMEOUT_SECONDS`, default 5). The
regression test now uses a socket that accepts connections but never replies, which is the
real failure mode. A second finding: with `localhost` in the URL, the timeout was paid twice
(10s), because libpq tries `::1` and then `127.0.0.1` and applies the timeout to each. The
URLs now use `127.0.0.1`.

Lesson: every network call needs a timeout, and a failure test should reproduce the actual
way things fail, not the most convenient one.

### Alternatives rejected

| Alternative | Why not |
|---|---|
| `Base.metadata.create_all()` | No history, no downgrade, can't evolve a live database. |
| PostgreSQL `ENUM` types | Harder to change later (see above). |
| `SERIAL` | Legacy; identity columns are standard SQL and safer with explicit inserts. |
| SQLite for tests | No exclusion constraints, no `FOR UPDATE`. Tests would pass on code that fails in production. |
| Separate `start`/`end` columns checked with a trigger | A trigger that checks for overlap has the same race as application code unless it locks; the exclusion constraint is atomic. |

### Likely questions

- **Why an exclusion constraint instead of checking in code?** A check in code is
  check-then-act: two transactions can both see "free" and both insert. The constraint is
  checked by the database at insert time using its index, so the second insert fails no
  matter how the requests interleave.
- **What does `btree_gist` do?** GiST indexes natively support ranges, not plain integers.
  `btree_gist` adds GiST support for scalar types so `room_id WITH =` can share the index
  with the date range.
- **Why `[)`?** Checkout day is not a night stayed, so back-to-back bookings must be allowed.
- **Is your schema normalised?** 3NF except `rooms.hotel_id`, kept for a uniqueness rule and
  query convenience, with a composite FK guaranteeing consistency.
- **Why store `total_price`?** It's a historical fact, not derived data; room prices change.
- **Why NUMERIC not FLOAT?** Exactness for money.
- **Why a separate test database?** Tests rebuild the schema from migrations and roll back
  every test. That must never happen to development data.
- **Why does `/health` check the database?** A process that is up but can't reach its
  database can't serve requests. The load balancer or orchestrator should know that.

## Milestone 2: Auth and catalog

### What was built

- `POST /auth/register`, `POST /auth/login` (returns a JWT), bearer-token dependency,
  admin role check.
- `GET /hotels` (city filter, pagination), `GET /hotels/{id}` (with room types).
- Admin: `POST /admin/hotels`, `/admin/hotels/{id}/room-types`, `/admin/hotels/{id}/rooms`.
- `scripts/create_admin.py`: registration always creates `user` accounts, so the first
  admin is created from the command line.
- `scripts/seed.py`: 200 hotels across 20 cities, 10,000 rooms, 200,000 bookings by default.
- Tests for security helpers, auth, catalog endpoints and the seed generator.

### How JWT auth works here

A JWT is three base64 parts: `header.payload.signature`. The payload holds claims:
`sub` (user id), `iat` (issued at), `exp` (expiry). The server signs header+payload with
HMAC-SHA256 using `JWT_SECRET`. On each request it recomputes the signature; if anyone
changed the payload (e.g. `sub`), the signature no longer matches. The payload is only
encoded, not encrypted, so nothing secret goes in it.

- **Algorithm pinned** (`algorithms=["HS256"]` when decoding). Otherwise an attacker could
  send a token with `"alg": "none"` and no signature. There's a test for this.
- **`exp`, `iat`, `sub` required**: a token without an expiry would be valid forever.
- **Role read from the database, not the token.** If an admin is demoted, the next request
  is already forbidden (tested). Cost: one primary-key lookup per request.
- **Trade-off of stateless tokens:** a token can't be revoked before it expires. Mitigations
  (not built): short expiry plus refresh tokens, or a denylist of token ids.

### Passwords

- **Argon2id** (`argon2-cffi`). Memory-hard, so GPU cracking is expensive; won the Password
  Hashing Competition. The salt and parameters are stored inside the hash string.
  bcrypt would also be fine but silently truncates passwords at 72 bytes. passlib, often
  seen in tutorials, is unmaintained.
- **Same error for unknown email and wrong password**, and an unknown email still runs a
  full hash verification, so neither the message nor the response time reveals which
  emails are registered.
- **Max length 128**: hashing is deliberately expensive, so unbounded input is a DoS vector.
- Emails are lowercased by the API; the DB `CHECK (email = lower(email))` backs that up.

### Duplicates are detected by constraints, not by a SELECT first

Register, add room type and add room just INSERT and translate the unique/foreign-key
violation into 409 or 422, using the constraint name PostgreSQL reports. A "check first"
SELECT would be the same check-then-act race as double booking: two concurrent requests
can both see "not taken". This is the same idea as the booking exclusion constraint,
applied to something simpler.

### 401 vs 403

401: we don't know who you are (missing, malformed, expired token). Sent with
`WWW-Authenticate: Bearer`, as the HTTP spec requires. 403: we know who you are and
you're not allowed.

### Pagination

Offset pagination (`LIMIT page_size OFFSET (page-1)*page_size`) with `ORDER BY id`.
Without `ORDER BY`, PostgreSQL may return rows in any order, so a hotel could appear on
two pages or none. The response includes `total` so clients can render page numbers.

Trade-off: `OFFSET 10000` still reads and discards 10,000 rows, and rows inserted between
requests shift pages. Keyset pagination (`WHERE id > :last_seen ORDER BY id LIMIT n`) fixes
both but can't jump to page N. For 200 hotels offset is fine; for bookings history keyset
would be the better choice.

### Case-insensitive city search

The filter is `lower(city) = lower(:city)`. A plain B-tree index on `city` can't serve that,
because the indexed value is `city`, not `lower(city)`; it would need an expression index
`ON hotels (lower(city))`. In Milestone 3 I tested that index and the planner didn't use it:
the hotels table is only a few pages, so a sequential scan is cheaper. Not added (see the
Milestone 3 section on indexes).

### Seed script

- **COPY for bookings**: PostgreSQL's bulk-load protocol streams rows without per-statement
  overhead. Hotels, room types, rooms and users use multi-row `INSERT ... RETURNING`
  because their generated ids are needed for the foreign keys of the next table.
- **Payments in one set-based statement**: `INSERT INTO payments SELECT ... FROM bookings
  WHERE status = 'confirmed'`. One round trip instead of building rows in Python.
- **Bookings never overlap**: per room, stays and gaps are laid out sequentially. If the
  generator were wrong, the exclusion constraint would reject the COPY.
- **Fixed random seed** (`--random-seed`, default 42): the same arguments give the same
  data, tested by fingerprinting two runs. Dates are relative to today, so there is always
  future inventory.
- **Skewed distribution**: big cities get more hotels, cheap room types are more common.
  Uniform data makes every query look the same and hides index effects.
- **One shared password hash** for seeded users: Argon2 is slow on purpose.
- `ANALYZE` afterwards so the query planner has statistics for the new data.
- Refuses to run on a non-empty database unless `--reset` is given.

### Testing approach

Each test runs in a transaction that is rolled back. The session uses
`join_transaction_mode="create_savepoint"`, so a service's `commit()` becomes a savepoint
release: the service code is exercised unchanged and nothing persists between tests.

### Why identity values have gaps

Sequences (and identity columns) are not transactional: a rolled-back insert still
consumes its id. This is deliberate. Making sequences transactional would force every
inserting transaction to wait for the previous one. Ids are unique, not gapless.

### Alternatives rejected

| Alternative | Why not |
|---|---|
| Server-side sessions | Needs a session store; JWT keeps the API stateless. |
| Role inside the JWT | Stale until expiry; demotion wouldn't take effect. |
| OAuth2 password form (`application/x-www-form-urlencoded`) for login | JSON body is consistent with the rest of the API. |
| bcrypt / passlib | 72-byte truncation / unmaintained. |
| SELECT-then-INSERT for duplicates | Race condition. |
| Keyset pagination for hotels | Can't jump to page N; offset is fine at this size. |

### Likely questions

- **What's in your JWT and how is it verified?** `sub`, `iat`, `exp`, HMAC-SHA256 signed;
  verification recomputes the signature with the server secret and checks expiry.
- **Can you log a user out?** Not server-side before expiry; that's the stateless trade-off.
  Short-lived tokens plus refresh tokens or a denylist would fix it.
- **Why Argon2?** Memory-hard, salted, current best practice.
- **How do you prevent user enumeration on login?** Same message and same work for
  unknown email and wrong password.
- **Why not check if the email exists before inserting?** Race condition; the unique
  constraint is the only reliable check.
- **401 or 403?** Unauthenticated vs authenticated-but-not-allowed.
- **Offset vs keyset pagination?** Above.
- **Why COPY in the seed script?** Fastest bulk load; no per-row statement overhead.
- **Can a user make themselves admin at registration?** No: the request schema has no
  `role` field, so it's ignored (tested).

## Milestone 3: Availability and booking

### What was built

- `GET /hotels/{id}/availability` and `GET /availability?city=` (city-wide search, the
  query the Milestone 4 benchmark measures).
- `POST /bookings` (hold), `POST /bookings/{id}/confirm`, `POST /bookings/{id}/cancel`,
  `GET /bookings/me`, `GET /bookings/{id}`.
- `services/locking.py`: the three strategies, selected by `BOOKING_STRATEGY`.
- `app/worker.py`: expires lapsed holds every `WORKER_INTERVAL_SECONDS`.
- Migrations: `0002` (payment attempts), `0003` (one partial index for the worker).
- `scripts/exclusion_toggle.py`: test-only removal of the exclusion constraint.
- Tests: availability, the booking flow, idempotency, access rules, each strategy, real
  concurrent races, the worker, the toggle.

### The availability query

```sql
SELECT h.id, ..., rt.id, rt.name, rt.capacity, rt.base_price_per_night,
       rt.base_price_per_night * :nights AS total_price,
       array_agg(r.id ORDER BY r.room_number) AS room_ids
FROM hotels h
JOIN room_types rt ON rt.hotel_id = h.id
JOIN rooms r       ON r.hotel_id = rt.hotel_id AND r.room_type_id = rt.id
WHERE h.id = :hotel_id                      -- or: lower(h.city) = lower(:city)
  AND rt.capacity >= :guests
  AND NOT EXISTS (
        SELECT 1 FROM bookings b
        WHERE b.room_id = r.id
          AND b.status IN ('held', 'confirmed')
          AND daterange(b.check_in, b.check_out, '[)') && daterange(:check_in, :check_out, '[)')
          AND (b.status = 'confirmed' OR b.hold_expires_at > now())
      )
GROUP BY h.id, rt.id
ORDER BY h.id, rt.base_price_per_night, rt.id
```

Reading it top to bottom:
1. Join hotel → room types → rooms. The rooms join uses both `hotel_id` and
   `room_type_id`, matching the composite foreign key.
2. Keep room types big enough for the party.
3. `NOT EXISTS`: drop a room if *any* active booking of it overlaps the requested stay.
   `&&` is "ranges overlap"; with `[)` a stay ending on the 15th doesn't overlap one
   starting on the 15th.
4. The last condition treats a hold past its expiry as free even if the worker hasn't
   marked it expired yet.
5. Group the surviving rooms by room type, count them, and price the stay.

**Why `NOT EXISTS`** and not `LEFT JOIN ... WHERE b.id IS NULL` or `NOT IN`: it says
exactly "no matching row exists", PostgreSQL turns it into an anti-join that stops at the
first match, and unlike `NOT IN` it isn't broken by NULLs.

**Index used:** `ex_bookings_no_overlap`. The GiST index behind the exclusion constraint
is on `(room_id, daterange(check_in, check_out, '[)'))` for active bookings, which is
exactly the shape of the `NOT EXISTS` probe. The constraint's index does double duty.

### Indexes (decided from EXPLAIN ANALYZE on the seeded data, not guessed)

| Query | What served it | Decision |
|---|---|---|
| Availability `NOT EXISTS` | GiST index of the exclusion constraint | nothing new |
| Overlap check / stale-hold expiry for one room | same GiST index | nothing new |
| `GET /bookings/me` | `uq_bookings_user_id_idempotency_key` (`user_id` is its first column) | nothing new |
| City filter on hotels | sequential scan; an index on `lower(city)` was tried and **not used** (the table is a few pages) | not added |
| Rooms of a hotel by type | `uq_rooms_hotel_id_room_number`; an index on `(hotel_id, room_type_id)` was used but the difference was within run-to-run noise | not added |
| Worker: lapsed holds | sequential scan of all bookings | **added** `ix_bookings_held_expiry ON bookings (hold_expires_at) WHERE status = 'held'` |

The worker index is *partial*: only live holds are in it, so it stays tiny no matter how
many bookings accumulate. During development the worker's query went from a full scan to
a single index page on the seeded data.

A plain index on `bookings.user_id` (the foreign key) isn't needed for the same reason:
the composite unique index already starts with `user_id`.

**Bug found while doing this:** the overlap check was slow because SQLAlchemy sent
`room_id = $1::INTEGER` while the column is `BIGINT`. `btree_gist`'s operator class only
covers `bigint = bigint`, so the GiST index could filter on dates but not on room, and
scanned thousands of entries. Binding ids as `BigInteger` fixed it. (Plain B-tree indexes
handle `bigint = integer` fine, which is why it's easy to miss.) EXPLAIN showed `room_id`
in a `Filter` line instead of the `Index Cond` line; that's what to look for.

### Why naive check-then-insert fails

```
time   Transaction A                       Transaction B
 1     SELECT overlap? -> none
 2                                         SELECT overlap? -> none
 3     INSERT booking; COMMIT
 4                                         INSERT booking; COMMIT   <- double booking
```
Each SELECT was correct when it ran. The decision was stale by the time of the INSERT.
`test_naive_check_then_insert_double_books` plays out exactly this interleaving.

### Why READ COMMITTED alone doesn't prevent it

READ COMMITTED only promises you won't see *uncommitted* data. At step 2, A's booking isn't
committed, so B correctly sees nothing. No isolation level makes B "wait to see" a row that
doesn't exist yet; preventing this needs a lock, a constraint, or SERIALIZABLE.

### The three strategies

**Pessimistic** (`SELECT id FROM rooms WHERE id = :room_id FOR UPDATE`, then check, then
insert): the room row acts as a mutex for that room. B blocks at the lock until A commits.
It works *because* of READ COMMITTED: B's next statement takes a fresh snapshot and sees
A's booking. Under REPEATABLE READ, B keeps the snapshot from before it waited, misses
A's booking and double-books. `test_pessimistic_lock_relies_on_read_committed` shows both
outcomes. The lock is only on that one room, so bookings for other rooms aren't affected.

**Constraint** (default): just INSERT; the exclusion constraint checks overlaps
atomically, using its index, at insert time. If B conflicts with A's uncommitted row,
PostgreSQL makes B wait for A's outcome, then raises `exclusion_violation` (SQLSTATE
23P01) if A committed. We map that to 409.

**Optimistic** (not implemented, discussed): add a `version` column to rooms; read it,
check availability, then `UPDATE rooms SET version = version + 1 WHERE id = :id AND
version = :read_version` in the same transaction as the INSERT. If 0 rows updated,
someone else booked meanwhile: retry or 409. No waiting, but under heavy contention for
the same room most attempts fail and retry.

| | Naive | Pessimistic | Optimistic | Constraint |
|---|---|---|---|---|
| Correct under concurrency | no | yes | yes | yes |
| Contention behaviour | n/a | waits in line | fails and retries | waits for the conflicting row, then fails fast |
| Guarantee lives in | nowhere | every code path that books | every code path that books | the database schema |
| Survives a buggy new code path / manual SQL | no | no | no | **yes** |
| Cost | none | lock held for the transaction | extra UPDATE, retries | GiST index maintenance on writes |
| Portability | any DB | any DB | any DB | PostgreSQL-specific |

**Why constraint is the default:** the guarantee holds for every writer (API, admin
scripts, future services) without anyone having to remember to lock. Its index also serves
the availability search. Pessimistic is the explained alternative: portable, and
appropriate when the rule can't be expressed as a constraint (e.g. "at most N bookings
per day across rooms").

**SERIALIZABLE** would also prevent the anomaly (PostgreSQL detects the read/write
dependency and aborts one transaction with SQLSTATE 40001), but every booking path then
needs retry logic, and the abort rate rises under contention.

**Test-only toggle:** with the constraint in place, naive and pessimistic would be
protected by it and we couldn't tell whether the strategy itself works. So the
pessimistic race test and the Milestone 4 experiment drop it on the test database first.
That lives in `scripts/exclusion_toggle.py`, refuses any database not named `*_test` or
when `APP_ENV=production`, and is never in the migration path. A test checks the
restored constraint is identical to the migration's.

### Isolation level

All transactions run at **READ COMMITTED**, set explicitly on the engine (it's
PostgreSQL's default, but the strategies depend on it, so it's stated, not assumed).
Correctness comes from row locks and constraints, not from a stricter isolation level.

### Holds and expiry

- `POST /bookings` inserts `status = 'held'` with `hold_expires_at = now() + HOLD_MINUTES`.
  The database clock is used for every time comparison, so app-server clock drift can't
  extend or shorten a hold.
- A hold blocks the room (it's in the exclusion constraint) until confirmed, cancelled or
  expired.
- **Why the booking path doesn't rely on the worker:** before checking availability, each
  strategy runs `UPDATE bookings SET status = 'expired' WHERE room_id = :room AND status =
  'held' AND hold_expires_at <= now() AND <overlaps the requested dates>` inside the same
  transaction. If the worker is down, slow, or hasn't run yet, a lapsed hold still can't
  block a new booking. The availability query likewise ignores lapsed holds. The worker
  just keeps stored statuses tidy.
- The worker uses `FOR UPDATE SKIP LOCKED`: it skips holds that a confirm or cancel has
  locked right now (that transaction decides their fate), and several workers can run
  without blocking each other. It works in batches so one sweep never holds thousands of
  row locks.

### Confirm, cancel and payments

- Confirm and cancel start with `SELECT ... FROM bookings WHERE id = :id FOR UPDATE`.
  That serialises confirm vs cancel vs worker for the same booking: e.g. a cancel can't
  slip in between "payment succeeded" and "status = confirmed".
- Confirm in one transaction: lock booking → if hold lapsed, mark expired and return 409 →
  charge (mock) → insert payment row → set confirmed → commit.
- Confirming an already confirmed booking returns it without charging again; cancelling
  twice is a no-op. Retries are safe.
- **Payment attempts (design change from the original spec):** the first schema had
  `UNIQUE (booking_id)` on payments, so a declined card blocked any retry. Migration 0002
  replaces it with a partial unique index, `UNIQUE (booking_id) WHERE status =
  'succeeded'`: any number of failed attempts, at most one success. The database itself
  guarantees no booking is paid twice, even with concurrent confirms. A declined payment
  returns 402 and the hold stays active.
- **Known trade-off:** a real payment provider call shouldn't happen while holding a row
  lock (the call can take seconds; everything else touching that booking waits). The
  production pattern is: mark the booking `payment_pending` and commit, call the provider
  outside any transaction, then record the result in a second transaction, with a
  reconciliation job for crashes in between. The mock is instant, so it's done inline here.

### Idempotency keys

A client that times out doesn't know whether its booking was created. Retrying could
create a second hold. With `Idempotency-Key`:
- First request: the key is stored on the booking (`UNIQUE (user_id, idempotency_key)`).
- Same key, same body: the original booking is returned with the original 201, plus an
  `Idempotent-Replayed: true` header. Nothing new is created.
- Same key, different body: 422, because it's almost certainly a client bug.
- Two concurrent requests with the same key: both may pass the lookup, but the unique
  constraint lets only one insert win; the loser catches the violation and returns the
  winner's booking.
- Keys are per user, so two users can't collide.
- Only successful creations are remembered. If the first attempt got 409, a retry runs
  again (and may succeed if the room was freed).

### Access rules

Owner or admin can read, confirm or cancel a booking; anyone else gets 403.

### Gotchas worth knowing

- **`now()` is the transaction start time**, not the wall clock; stable within one
  transaction. Tests rely on that.
- **Session identity map:** after taking a row lock, the code reloads the row with
  `populate_existing`, otherwise SQLAlchemy could hand back an older copy of the object
  it already had in memory.
- **Sequences have gaps:** a booking attempt that fails with 409 still consumes an id.

| Alternative | Why not |
|---|---|
| Naive as default | Double-books; exists only for the experiment. |
| REPEATABLE READ for bookings | Breaks the pessimistic strategy (tested). |
| SERIALIZABLE | Works, but every path needs retry logic; aborts under contention. |
| Availability filtered in Python | Loads every booking into the app; the database does it with an index. |

### Likely questions

- **Walk me through the availability query.** See above: joins, capacity filter,
  `NOT EXISTS` over overlapping active bookings, group by room type.
- **Which index does it use?** The exclusion constraint's GiST index.
- **Why does check-then-insert fail?** Two transactions both check before either inserts.
- **Why doesn't READ COMMITTED prevent it?** It hides uncommitted rows; the conflicting row
  isn't committed yet when the second check runs.
- **Pessimistic vs constraint vs optimistic?** Table above.
- **Why READ COMMITTED with the pessimistic strategy?** Fresh snapshot after the lock wait.
  REPEATABLE READ would double-book (tested).
- **What if the worker dies?** Nothing breaks: the booking path and availability query
  ignore lapsed holds; statuses just stay stale until it's back.
- **What does `SKIP LOCKED` do?** Skip rows another transaction has locked instead of
  waiting; lets multiple workers share a queue.
- **How do idempotency keys work?** Above.
- **Can a booking be paid twice?** No: partial unique index on successful payments, plus
  the row lock on the booking during confirm.
- **What would you change for a real payment provider?** Don't call it while holding a
  lock; use a pending state and reconciliation.

## Milestone 4: Experiments

### What was built

- `scripts/concurrency_test.py`: 100 simultaneous bookings of one room through a real
  uvicorn server, per strategy, then counts double bookings in SQL.
- `scripts/benchmark_search.py`: times the city search, the hotel search and the worker's
  expiry sweep in three index states, and saves the EXPLAIN ANALYZE plans.
- `scripts/experiment_utils.py`: shared helpers (run metadata, percentiles, Markdown tables).
- A fix for a pool deadlock the concurrency experiment uncovered, with a regression test
  (`tests/test_db_pool.py`).
- Results are committed in `results/`. Every number below is copied from those files.

Both scripts run only against `hotel_booking_test` (they go through the same
`ensure_test_database` guard as the exclusion toggle) and restore the production schema
when they finish.

### Experiment 1: 100 users book the same room at once

**Setup:** 100 clients each send one `POST /bookings` for the same room and the same three
nights. All 100 HTTP connections are opened first, then the requests are released at the
same instant. One API process, DB pool 10 + overflow 10, READ COMMITTED. Five runs per
scenario. After each run, SQL counts pairs of active bookings for the room whose dates
overlap; anything above 0 is a double booking.

| Scenario | 201 booked | Overlapping pairs | Runs that double-booked | Total time, median (s) |
|---|---|---|---|---|
| naive, constraint dropped | 1 to 3 | 0 to 3 | 2 of 5 | 2.126 |
| naive, with constraint | 1 | 0 | 0 of 5 | 2.122 |
| pessimistic, constraint dropped | 1 | 0 | 0 of 5 | 2.240 |
| constraint (production) | 1 | 0 | 0 of 5 | 2.330 |

Every other response was a 409; there were no other errors in any run.

**What it shows:**
- **Naive check-then-insert double-books under real load,** not just in the hand-built
  interleaving of the Milestone 3 test. Run 1 created 3 bookings for the same nights.
- **It doesn't happen every time** (2 of 5 runs). A race depends on timing, so a test that
  passes once proves nothing. That's why the experiment repeats each scenario.
- **The constraint rescues even the naive code** ("naive, with constraint": 1 booking every
  run). The guarantee lives in the schema, so a buggy code path can't break it.
- **Pessimistic locking alone is correct** with the constraint dropped: 1 booking every run.
- **Speed differences between strategies are within noise.** Medians range from 2.12 to
  2.33 s, and the per-run numbers overlap (see `results/concurrency.md`). Correctness, not
  speed, is what separates them in this test.

### The bug the experiment found: a connection pool deadlock

**Symptom:** with more concurrent requests than pool connections, the API stalled until the
pool's 30-second timeout and then returned 503s. Reproduced with plain `/health`: 100
concurrent requests gave 60 × 200 and 40 × 503, median latency 30.4 s.

**Cause:** FastAPI runs sync endpoints and sync dependencies on a thread pool of 40
threads. The pool has 20 connections. Requests beyond those 20 took a thread and then
blocked inside it, waiting for a connection. Once all 40 threads were blocked, the requests
that *did* hold connections couldn't get a thread to finish and close their session, so
they never handed the connection back. Nothing could make progress until the pool timeout
fired, which is where the 503s and the 30 s latency came from.

```
40 threads:  [requests holding a connection, waiting for a thread to finish]
           + [requests holding a thread, waiting for a connection]
           -> each side waits for the other
```

**Fix:** `get_db` is now an async dependency. Before opening a session it waits on a
semaphore sized to the pool's capacity (`pool_size + max_overflow`). Waiting happens in
the event loop, which costs no thread, so a request only takes a thread once a connection
is certain to be free. Closing the session runs in its own one-slot limiter, so handing a
connection back never waits for a busy thread. The semaphore is created in the app's
lifespan so it belongs to the event loop that serves requests.

**After:** all 100 concurrent `/health` requests returned 200, the slowest in 0.605 s.

**Regression test:** a pool of 2 connections and 60 concurrent requests, more than the 40
threads plus the pool. On the old code 25 of 60 got 503; with the fix all 60 return 200.

**Lesson:** acquiring one bounded resource (a connection) while holding another (a thread)
can deadlock when both run out. Wait for the scarcer one before taking the other.

### Experiment 2: search latency by index state

**Setup:** the seeded dataset (5,000 users, 200 hotels, 10,000 rooms, 200,000 bookings),
the application's exact SQL, 10 warm-up runs, then 100 timed runs per query and state. All
states use the same seeded list of cities, hotels, dates and party sizes. Latency is
measured from the Python client, so it includes the round trip to PostgreSQL in Docker.

Index states on `bookings`:
- **none:** no index (GiST constraint dropped, migration 0003 downgraded).
- **btree:** a plain B-tree on `room_id` only. This is the obvious index anyone would add,
  so it is a fairer comparison than "no index at all".
- **production:** the GiST index behind the exclusion constraint, plus the partial
  `ix_bookings_held_expiry` from 0003.

| Query | none p50 / p95 (ms) | btree p50 / p95 (ms) | production p50 / p95 (ms) |
|---|---|---|---|
| City search | 6600.13 / 35370.39 | 7.58 / 13.88 | 6.62 / 11.56 |
| Hotel search | 47.39 / 89.79 | 4.07 / 5.21 | 3.86 / 4.71 |
| Worker expiry sweep | 22.11 / 24.85 | 20.65 / 24.92 | 2.26 / 2.71 |

Index sizes: GiST `ex_bookings_no_overlap` 16 MB; the B-tree on `room_id` 1568 kB;
`ix_bookings_held_expiry` 8192 bytes.

**What it shows:**

1. **No index is a disaster, and the plan shows why.** The planner estimated the joins
   would produce 1 candidate room; there were 30. Expecting to probe bookings once, it
   chose a nested loop with a parallel sequential scan of `bookings` on the inner side,
   and then ran that scan once per candidate room (`loops=30` in
   `results/explain/city_search_none.txt`). Median 6.6 s, p95 35 s.
2. **For search, GiST and a plain B-tree perform about the same.** City search median
   6.62 vs 7.58 ms; hotel search 3.86 vs 4.07 ms. Both plans probe `bookings` once per
   candidate room with an index scan; only the index differs. GiST is also about ten
   times larger (16 MB vs 1568 kB).
3. **So the honest justification for GiST is the constraint, not speed.** The exclusion
   constraint can't exist without a GiST index. Once it exists, the availability query
   reuses it, so search needs no extra index. "GiST makes search faster" is not what this
   data shows.
4. **The partial index does its job.** The worker's sweep goes from a sequential scan of
   all 200,000 bookings (20.65 ms with the B-tree, which doesn't help this query) to
   2.26 ms. In EXPLAIN, server-side time drops from 18.905 ms to 0.102 ms. The index is
   8 kB because it only holds held bookings.

**Caveat:** the EXPLAIN times in `results/search_benchmark.md` are for the first parameter
set only; the latency table is the one to quote.

### Alternatives rejected

| Alternative | Why not |
|---|---|
| Testing the race with the constraint in place | The constraint would hide whether the strategy itself works. |
| One run per scenario | Naive double-booked in only 2 of 5 runs; one run could miss it. |
| Comparing GiST only against "no index" | Any index beats no index; the B-tree state answers the real question. |
| Raising the thread or DB pool size to fix the deadlock | Moves the limit instead of removing it; a larger burst deadlocks again. |
| Switching the whole app to async SQLAlchemy | A much larger change; one async dependency fixes the cause. |

### Likely questions

- **Did you actually see a double booking?** Yes: naive with the constraint dropped
  created up to 3 bookings for the same nights, in 2 of 5 runs.
- **Why not every run?** It's a race; it only fails when two checks run before either
  insert commits. That's why each scenario runs 5 times.
- **Which strategy is fastest?** No measurable difference in this test: medians 2.12 to
  2.33 s, with overlapping runs.
- **Why spend 16 MB on GiST if a B-tree searches as fast?** The exclusion constraint
  requires it, and the constraint is what guarantees no double booking. Search reuses it.
- **Why was the no-index case so slow?** A row estimate of 1 against an actual 30 made the
  planner pick a nested loop that scanned all bookings 30 times.
- **Explain the deadlock.** Threads blocked waiting for connections while the connection
  holders waited for threads. Fix: wait for a connection slot in the event loop first.
- **Why does the regression test send 60 requests?** It must exceed the 40 worker threads
  plus the pool; otherwise threads never run out.
- **Why a partial index for the worker?** Its query only looks at held bookings, a tiny
  fraction of the table. Indexing only those keeps the index at 8 kB.

## Milestone 5: Production setup

### What was built

- `Dockerfile`: multi-stage, runs as an unprivileged user. One image serves the API, the
  worker and the migration step; only the command differs.
- `docker-compose.yml`: `db`, `migrate`, `api`, `worker`, `nginx`.
- `deploy/nginx.conf`: reverse proxy in front of the API.
- `.github/workflows/ci.yml`: lint, tests against PostgreSQL, Docker image build.
- uvicorn's own server and access logs now go through the JSON formatter too
  (`tests/test_logging_config.py`).

### Why Docker, Nginx and CI at all

- **Docker:** the same image runs on my laptop, in CI and on the server, with exact
  dependency versions baked in. "Works on my machine" stops being a category of bug, and
  deploying is "pull/build and start", not a list of manual install steps.
- **Nginx:** the one public entry point. The API container isn't published on the host at
  all, so nothing reaches uvicorn except through nginx. It's the place for things that
  shouldn't live in application code: TLS termination (Milestone 6, optional), request size
  limits, timeouts, and later rate limiting or serving several API replicas.
- **CI:** every push proves that lint passes, the tests pass against a real PostgreSQL, and
  the image builds. A broken commit is caught by a machine, not by whoever deploys next.

### The image

**Two stages.** The build stage creates a virtualenv and installs `requirements.txt` into
it. The runtime stage starts again from the slim base and copies in only the virtualenv and
the application code. pip and setuptools are uninstalled from the virtualenv before it's
copied: nothing needs them at runtime.

**Measured** (`docker image inspect`, Docker Desktop on this machine):

| Image | Size |
|---|---|
| `python:3.11-slim-bookworm` base | 206,918,255 bytes (207 MB) |
| Final multi-stage image | 338,569,124 bytes (339 MB) |
| First multi-stage build, with pip and setuptools still in the venv | 375,588,772 bytes (376 MB) |
| Same app, naive single stage (`pip install` in one `FROM`, runs as root) | 407,207,584 bytes (407 MB) |

The single-stage image kept a 27 MB pip download cache in `/root/.cache/pip`. The
virtualenv itself went from 126 MB to 98 MB after removing pip (17 MB) and setuptools
(11 MB).

**Honest framing:** every dependency here ships as a prebuilt wheel, so there's no compiler
to leave behind, which is where multi-stage usually saves the most. Here it saves the pip
cache and the install tooling, and keeps the runtime stage short and obvious. Most of the
remaining size is the Python base image itself.

**Non-root.** The container runs as `app` (uid 999, checked with `id`). If someone found a
bug that let them run code in the API, they'd be an unprivileged user inside the container,
not root.

**`.dockerignore`** keeps `.env`, `.git`, `.venv`, tests and results out of the build
context, so secrets can't end up in an image layer by accident.

### Migrations: a one-off service, not on API startup

`migrate` runs `alembic upgrade head` and exits. `api` and `worker` start only after `db`
is healthy *and* `migrate` exited with code 0 (`service_completed_successfully`).

- If a migration fails, the API doesn't start against a half-migrated schema; the
  failure is visible as a non-zero exit on one container.
- Running migrations inside every API process on startup breaks as soon as there are two
  replicas: both try to migrate at once.
- The same command works by hand on a server: `docker compose run --rm migrate`.

### Compose details worth knowing

- **Healthchecks gate startup.** `db` uses `pg_isready`; `api` calls its own `/health`
  (which runs `SELECT 1`), with a Python one-liner because the slim image has no curl.
  nginx starts only once the API is healthy.
- **`DATABASE_URL` differs inside the stack.** On the host it's `127.0.0.1:5434`; inside the
  compose network it's `db:5432`. Compose builds the in-stack URL from the `POSTGRES_*`
  variables, so there's one source for the password. Consequence: the password must be
  URL-safe.
- **The database port is published on loopback only** (`127.0.0.1:5434`), so local tests
  still work but other machines can't reach PostgreSQL. On a server this matters.
- **Proxy headers.** uvicorn runs with `--proxy-headers --forwarded-allow-ips "*"`, so the
  access log shows the client address nginx forwarded instead of nginx's. Trusting any
  address is safe only because the API port isn't published; nginx is the only thing that
  can reach it.
- **Restart policy** `unless-stopped` on long-running services; `migrate` never restarts.

### Bug found while testing: nginx 502 after the API container was recreated

**Symptom:** after rebuilding the stack, `/health` through nginx returned 502 while the API
container itself was healthy.

**Cause:** nginx resolves `server api:8000` once, when it starts, and keeps that IP. The
rebuild recreated the API container, which came back on a different IP (172.18.0.4 before,
172.18.0.3 after). nginx's error log showed it still connecting to 172.18.0.4.

**Fix:** use Docker's internal DNS server (`resolver 127.0.0.11 valid=10s`) and mark the
upstream server `resolve`, so nginx looks the name up again. This needs nginx 1.27.3 or
newer, so the image is pinned to `nginx:1.27.5-alpine`. Unlike the common
`set $upstream ...; proxy_pass $upstream;` trick, it keeps the `upstream` block and its
connection reuse (`keepalive`).

**Verified:** recreated the API so it moved from 172.18.0.6 to 172.18.0.4 without restarting
nginx. Of 15 requests at one per second, the first timed out against the old IP; the next
14 returned 200.

**What that first failure means:** for up to `valid=10s` after the API moves, nginx can
still use the old address. With a single API container a redeploy has a short outage
anyway; removing that needs two replicas and rolling restarts.

### Smaller fix: uvicorn logs weren't JSON

The app's logs were JSON lines, but uvicorn installs its own plain-text handlers before it
imports the app, so its startup and access lines weren't. In a container all of these go to
one stream, which a log tool would then have to parse two ways. `configure_logging` now
removes uvicorn's handlers and lets its loggers propagate to the JSON handler. It also drops
uvicorn's `color_message` field, a copy of the message with terminal colour codes.

### CI

Three jobs, in parallel:

| Job | What it proves |
|---|---|
| lint | `ruff check` and `ruff format --check` pass |
| test | all tests pass against a fresh `postgres:16-alpine` service container |
| docker | the image builds, runs as non-root, and the app, worker and seed script import inside it |

- The secrets in `ci.yml` are throwaway values for a throwaway database that exists only

### End-to-end check through nginx

With the full stack up, a script went through nginx on port 80: health 200, register 201,
login 200, city availability 200, hold 201, the same request with the same
`Idempotency-Key` 201 with `Idempotent-Replayed: true`, the same room with a new key 409,

### Alternatives rejected

| Alternative | Why not |
|---|---|
| Single-stage image | Measured 407 MB vs 339 MB, ran as root, kept the pip cache. |
| Alpine Python base | Uses musl instead of glibc. When a package has no musl wheel, pip compiles it from source and the build needs a compiler. Slim avoids that class of problem. |
| Migrations on API startup | Races with more than one replica; a failed migration should stop the deploy, not crash-loop the API. |
| Publishing the API port as well | Bypasses nginx, and makes trusting proxy headers unsafe. |
| Restarting nginx after every API deploy | Fixes the symptom; re-resolving fixes the cause. |
| Unpinned third-party images (`nginx:latest`) | A rebuild could silently pull a different major version. PostgreSQL is pinned to major 16 (a new major needs a data upgrade); nginx to 1.27.5, because the config depends on a 1.27.3+ feature. |

### Likely questions

- **Why multi-stage?** The runtime image gets only the virtualenv and code, not pip, its
  cache or build tooling. Measured 339 MB vs 407 MB for a naive single stage. Honest caveat:
  with only prebuilt wheels the saving is modest; most of the size is the Python base.
- **Why non-root?** Limits what an attacker can do if they get code execution in the API.
- **How do migrations run?** A one-off `migrate` service; the API and worker wait for it to
  exit successfully.
- **What does nginx do here that uvicorn can't?** One public entry point, request size
  limits and timeouts now; TLS, rate limiting and load balancing across replicas later.
  Application code stays free of those concerns.
- **Why did nginx return 502?** It cached the API container's IP at startup. Fixed by
  re-resolving through Docker's DNS.
- **Is a deploy zero-downtime?** No: one API container, so a restart is a short outage.
  Zero downtime needs at least two replicas and rolling restarts.
- **How does CI test against PostgreSQL?** A service container; the tests rebuild the
  schema from the migrations at the start of the run.
- **Where would real secrets go?** GitHub encrypted secrets for CI; `.env` on the server
  (never committed), or a secrets manager on AWS.
