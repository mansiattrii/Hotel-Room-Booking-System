# Interview notes

Plain-language notes on what was built, why, and what I'd say if asked about it.
One section per milestone.

---

## Milestone 1: Setup and schema

### What was built

- Project skeleton, pinned dependencies, ruff config, `.env.example`.
- `docker-compose.yml` with PostgreSQL 16 (named volume, `pg_isready` healthcheck). An init
  script creates a second database, `hotel_booking_test`, used by pytest and the
  concurrency experiment so they never touch development data.
- `config.py`: every setting comes from environment variables (`pydantic-settings`).
- `db.py`: one SQLAlchemy engine and a session-per-request dependency.
- One hand-written Alembic migration for the full schema.
- `GET /api/v1/health`: runs `SELECT 1`; 200 if the database answers, 503 otherwise.
- A shared error format `{"error": {"code", "message"}}` for every non-2xx response.
- JSON-lines logging through the standard `logging` module.
- Tests that hit the real database with raw SQL to prove each constraint works.

### Schema in one picture

```
hotels 1──* room_types 1──* rooms 1──* bookings *──1 users
hotels 1──────────────────* rooms            bookings 1──0..1 payments
```

### Key decisions

**Sync, not async.** The bottleneck is the PostgreSQL connection pool, not Python threads.
Sync code keeps transactions, `SELECT ... FOR UPDATE` and isolation levels easy to read.
FastAPI runs sync endpoints in a thread pool, so requests still run in parallel and the
race condition in the concurrency experiment is real. Async would pay off for thousands of
slow concurrent connections (websockets, many outbound HTTP calls), which this API does not have.

**Hand-written migration.** Autogenerate cannot emit `CREATE EXTENSION btree_gist` and
renders the partial exclusion constraint poorly. The models still declare every constraint
so the code documents what the database enforces, but the migration is the source of truth.

**`NUMERIC(10,2)` for money.** Floats are binary fractions, so `0.1 + 0.2 != 0.3`. NUMERIC is
exact decimal arithmetic; Python reads it as `Decimal`.

**Status and role as `VARCHAR` + `CHECK`, not PostgreSQL `ENUM`.** Both restrict values.
Adding a value to an ENUM needs `ALTER TYPE` (and historically could not run inside a
transaction); changing a CHECK constraint is an ordinary migration.

**`BIGINT GENERATED BY DEFAULT AS IDENTITY` primary keys.** Identity columns are the
SQL-standard replacement for `SERIAL`. BIGINT because bookings is the table that grows
without bound; using it everywhere keeps FK types consistent.

**Composite foreign key `rooms(hotel_id, room_type_id) → room_types(hotel_id, id)`.**
A plain FK on `room_type_id` would allow room 101 of Hotel A to point at a room type of
Hotel B. The composite FK makes that impossible. It needs `UNIQUE (hotel_id, id)` on
room_types as its target, even though `id` alone is already unique.

**Exclusion constraint for double booking.**
```sql
EXCLUDE USING gist (room_id WITH =, daterange(check_in, check_out, '[)') WITH &&)
WHERE (status IN ('held', 'confirmed'))
```
Read it as: "no two rows may have equal `room_id` AND overlapping (`&&`) date ranges, among
rows that are held or confirmed". A UNIQUE constraint can only reject *equal* values; an
exclusion constraint generalises that to any operator, here "overlaps". It is enforced with
a GiST index, and `btree_gist` is the extension that lets a plain `bigint` (`room_id`) sit in
a GiST index next to the range.

**Half-open range `[)`.** A stay from the 10th to the 15th occupies the nights of the
10th–14th. The guest leaves on the 15th, so the next guest can arrive on the 15th.
`[10, 15)` and `[15, 18)` do not overlap; with a closed range `[]` they would share the 15th
and the back-to-back booking would be wrongly rejected. Tested in
`test_back_to_back_bookings_allowed`.

**Partial (`WHERE`) constraint.** Cancelled and expired bookings stay in the table as history
but must not block the room, so they are excluded from the constraint.

**Small extra constraints that turn bugs into errors.**
- `email = lower(email)`: the app normalises emails; the DB rejects anything that slipped
  through, so `A@x.com` and `a@x.com` can't become two accounts.
- `status <> 'held' OR hold_expires_at IS NOT NULL`: a hold without an expiry would block a
  room forever.
- `guests > 0`, prices positive, `star_rating BETWEEN 1 AND 5`.

**Additions to the given schema.**
- `bookings.guests`: needed to validate against room capacity, and it lets the idempotency
  check compare a repeated request's body against the stored booking without an extra
  "request hash" column.
- `UNIQUE (hotel_id, name)` on room_types: two "Deluxe" types in one hotel is a data error.

### Normalisation

The schema is in 3NF with one deliberate exception: `rooms.hotel_id`. It is derivable from
`room_type_id → room_types.hotel_id`, i.e. a transitive dependency. It is kept because:
1. `UNIQUE (hotel_id, room_number)` needs both columns in the same table.
2. "Rooms in hotel X" is a common query that would otherwise need a join.
The usual risk of denormalisation, the two copies disagreeing, is removed by the composite
foreign key, which forces them to match.

`bookings.total_price` is also stored rather than computed: prices change over time, and a
booking must keep the price the guest agreed to.

### Indexes in this milestone

Only those that come with constraints: primary keys, the UNIQUE constraints, and the GiST
index behind the exclusion constraint. Indexes for search and booking queries are added in
Milestone 3 as a separate migration, next to the queries that use them. That also lets the
Milestone 4 benchmark measure "without vs with" by downgrading and re-applying just that
migration.

### A bug found while verifying `/health`

With the db container stopped, `/health` hung forever instead of returning 503.
Docker Desktop's port proxy keeps accepting TCP connections on the host port even when the
container behind it is down. The driver's TCP connect succeeds, then waits indefinitely for
the PostgreSQL handshake. The unit test hadn't caught it because it used a closed port,
which fails instantly.

Fix: `connect_timeout` on the engine (`DB_CONNECT_TIMEOUT_SECONDS`, default 5). The
regression test now uses a socket that accepts connections but never replies, which is the
real failure mode. A second finding: with `localhost` in the URL, the timeout was paid twice
(10s), because libpq tries `::1` and then `127.0.0.1` and applies the timeout to each. The
URLs now use `127.0.0.1`.

Lesson: every network call needs a timeout, and a failure test should reproduce the actual
way things fail, not the most convenient one.

### Alternatives rejected

| Alternative | Why not |
|---|---|
| `Base.metadata.create_all()` | No history, no downgrade, can't evolve a live database. |
| PostgreSQL `ENUM` types | Harder to change later (see above). |
| `SERIAL` | Legacy; identity columns are standard SQL and safer with explicit inserts. |
| SQLite for tests | No exclusion constraints, no `FOR UPDATE`. Tests would pass on code that fails in production. |
| Separate `start`/`end` columns checked with a trigger | A trigger that checks for overlap has the same race as application code unless it locks; the exclusion constraint is atomic. |

### Likely questions

- **Why an exclusion constraint instead of checking in code?** A check in code is
  check-then-act: two transactions can both see "free" and both insert. The constraint is
  checked by the database at insert time using its index, so the second insert fails no
  matter how the requests interleave.
- **What does `btree_gist` do?** GiST indexes natively support ranges, not plain integers.
  `btree_gist` adds GiST support for scalar types so `room_id WITH =` can share the index
  with the date range.
- **Why `[)`?** Checkout day is not a night stayed, so back-to-back bookings must be allowed.
- **Is your schema normalised?** 3NF except `rooms.hotel_id`, kept for a uniqueness rule and
  query convenience, with a composite FK guaranteeing consistency.
- **Why store `total_price`?** It's a historical fact, not derived data; room prices change.
- **Why NUMERIC not FLOAT?** Exactness for money.
- **Why a separate test database?** Tests rebuild the schema from migrations and roll back
  every test. That must never happen to development data.
- **Why does `/health` check the database?** A process that is up but can't reach its
  database can't serve requests. The load balancer or orchestrator should know that.
